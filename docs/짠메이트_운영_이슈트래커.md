# 짠메이트 운영 이슈 트래커

> 최초 작성일: 2026-07-26
> MVP 기획서·개발로드맵과 별도로, 론칭 이후에도 계속 추적·재검토가 필요한 기술 부채·비용·인프라 이슈를 한곳에 모아두는 문서입니다. 코드 커밋 로그나 대화 기록을 뒤지지 않고 이 문서 하나만 보면 "지금 미뤄둔 게 뭐가 있고, 언제 다시 봐야 하는지"를 알 수 있게 하는 게 목적입니다. 기획서 11번(리스크)·로드맵 6주차(소프트 런칭 게이트)에 이미 있는 항목은 여기서 다시 쓰지 않고 링크만 겁니다.

각 항목은 다음 형식을 따릅니다: **현황 → 결정/상태 → 재검토 트리거**.

## 1. 신규 등록 이슈 (2026-07-26, 5주차 시드 반응 자동 생성 작업 중 발견)

### 1-1. 시드 페르소나 조회 성능 — `seed_personas` 테이블 분리 (백로그)

- **현황**: `app/api/cron/drip/route.ts`의 `getSeedPersonaIds()`가 크론 실행마다 `seed_contents_pool` 테이블 전체에서 `seed_user_id` 컬럼을 읽어와 JS에서 dedupe하는 방식으로 시드 페르소나 30명 목록을 구함. 지금은 400행 고정 + 하루 4회 실행이라 비용은 무시할 수준.
- **결정 (2026-07-26)**: 지금 당장 손대지 않음. 다음 스프린트에 가볍게 테이블을 분리하는 쪽으로 처리하기로 백로그 등록.
- **제안 방향**: `seed_contents_pool`에서 매번 파생시키지 말고, 30행짜리 전용 `seed_personas` 테이블(persona_id, nickname, niche 등)을 신설. 크론 조회 비용을 고정시키는 동시에, 현재 운영 문서에 UUID를 하드코딩해서 관리 중인 "시드 계정 KPI 제외 목록" 문제도 이 테이블 하나로 자연스럽게 해결됨(일석이조).
- **재검토 트리거**: `seed_contents_pool` row 수가 유의미하게 늘어나거나(시드 운영 기간 연장 등), 크론 실행 로그에서 이 조회 구간의 지연이 실제로 체감될 때.
- **관련 코드**: `app/api/cron/drip/route.ts` (`getSeedPersonaIds` 함수)

### 1-2. 시드 반응(Reactions) Bulk Insert 부분 실패 처리 — Best-effort로 결정 완료

- **현황**: `posts` insert는 성공했는데 그 직후의 `reactions` bulk insert만 실패하는 경우, 현재 코드는 재시도·롤백 없이 로그만 남기고 넘어감. 문제는 이게 영구적 실패라는 점 — 발행된 시드 콘텐츠는 `seed_contents_pool.published_at`이 이미 마감 처리돼서 다시 크론 대상이 되지 않음. 즉 이 타이밍에 실패하면 그 배치의 게시글들은 영구적으로 반응 0개로 남음.
- **결정 (2026-07-26)**: 그대로 Best-effort 유지(재시도 로직 추가 안 함). 근거는 세 가지 — ① 반응은 장식적 요소이지 서비스 코어 로직/데이터 정합성에 영향 없음. ② Vercel 서버리스 타임아웃 제약상, 여기서 재시도를 태우면 오히려 뒤에 이어지는 매칭 프리뷰 갱신·크론 정상 종료 자체가 타임아웃으로 죽을 리스크가 커짐. ③ 반응 0개 상태로 피드에 노출돼도 신규 오가닉 글과 섞이면 유저 입장에서 위화감 없음.
- **확인 방법**: Vercel 대시보드 → Logs/Observability에서 `시드 반응 insert 실패` 검색, 또는 Cron Jobs 탭의 실행 응답 JSON에서 `published`는 정상인데 `reactionsGenerated`가 비정상적으로 낮은 경우.
- **재검토 트리거**: 이 실패가 실제로 반복 관측되어 "반응 없는 시드 글"이 눈에 띄게 쌓이는 경우에만 재시도 로직 추가를 고려.
- **관련 코드**: `app/api/cron/drip/route.ts` (posts insert 직후 ~ reactions insert 블록)

## 3. 론칭 직전 DB 일괄 정리 체크리스트

테스트 중 쌓인 데이터를 실제 론칭 전에 한 번에 리셋하기 위한 항목. 지금 바로 실행하지 않고 론칭 직전에 실행 예정.

1. `posts` 테이블에서 시드 계정 30명 UUID + 그동안의 수동 테스트 게시물(이미지 테스트 포함) 전부 삭제
2. `seed_contents_pool.published_at`을 전부 `null`로 리셋 (400개 풀 재사용)
3. `matching_previews` 초기화 (론칭 후 첫 드립 크론 실행 시 자동 재생성)
4. 위 삭제로 `reactions` 테이블의 관련 row도 `ON DELETE CASCADE`로 함께 정리됨(별도 작업 불필요 — `post_id` FK가 `posts(id)` 참조, `ON DELETE CASCADE`로 정의돼 있음)
